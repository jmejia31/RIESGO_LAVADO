## 1. Objetivo

Fijar, antes de modificar el Form Builder o el backend, el contrato que debe sobrevivir sin pérdida en el ciclo:

`JSON plantilla -> Builder -> JSON -> API -> VER_JSON -> recarga -> Builder`

y en el ciclo de evaluación:

`selección de catálogo -> EVA_DATOS_JSON -> persistencia -> recarga por evaVersionId -> renderer -> misma selección/etiqueta`.

F6.0 es una fase de auditoría y decisión contractual. No implementa todavía el CRUD visual de catálogos ni modifica Oracle.

## 3. Principios contractuales obligatorios

El contrato v3 fija como reglas rectoras:

- la definición está versionada;
- la respuesta queda asociada a la versión exacta;
- una versión publicada es inmutable;
- los cálculos autoritativos pertenecen al servidor;
- los catálogos son autoritativos y pueden provenir de servicio/base de datos con respaldo embebido;
- el valor de catálogo almacenado es `codigo`;
- el valor presentado al usuario es `etiqueta`;
- la ausencia se representa con `null`;
- los campos usados no se eliminan físicamente: se desactivan;
- las fechas se representan en ISO 8601;
- una propiedad válida que el editor actual no entienda no puede desaparecer silenciosamente durante un round-trip.

### Decisión F6.0-DEC-01 — Cero pérdida silenciosa

**APROBADA.** El guardado bidireccional de F6 será semánticamente lossless. Toda propiedad contractual válida debe quedar en uno de estos estados:

1. **Editable y preservada:** la UI la entiende, permite modificarla y la reserializa.
2. **Solo preservada:** la UI todavía no la edita, pero la conserva opacamente al guardar.
3. **Transformada explícitamente:** existe una regla de compatibilidad documentada y testeada entre alias.
4. **Rechazada explícitamente:** el contrato la considera inválida y el usuario recibe un error verificable.

**Prohibido:** descartar una propiedad válida porque el Builder no la reconoce.

## 4. Contrato funcional v3 vs contrato reducido actual

### 4.1 Raíz / envelope

El contrato fuente contiene, entre otros:

- `tipoDocumento`
- `versionContrato`
- `estado`
- `idioma`
- `fechaGeneracion`
- `origen`
- `convenciones`
- `arquitecturaLogica`
- `roles`
- `flujoTrabajo`
- `definicionFormulario`

El `FormBuilderModel` actual trabaja directamente con:

- `codigoFormulario`
- `nombreFormulario`
- `descripcion?`
- `secciones`
- `catalogos?`
- `reglas?`

**Hallazgo F6-H01 — CRÍTICO:** el Builder actual no representa el envelope completo del contrato v3. Si recibe directamente el documento contractual completo, no existe round-trip completo de raíz.

**Decisión:** F6.1 deberá separar claramente **envelope contractual** y **definición editable**, preservando el envelope opacamente cuando no sea editable.

## 5. Secciones

- `identificador`
- `titulo`
- `orden`
- `activo`
- `visible`

El contrato reducido actual utiliza:

### Hallazgo F6-H02 — ALTO

Existe divergencia semántica `identificador` vs `clave`, y actualmente no se preservan necesariamente `activo`, `visible` ni metadatos adicionales de sección.

### Decisión F6.0-DEC-02

`identificador`/`clave` requieren una política de alias explícita. No se permitirá generar una identidad nueva por índice si la fuente ya tiene una identidad estable.

### Hallazgo F6-H03 — CRÍTICO

`normalizarJsonABuilderModel()` actualmente reduce cada campo a un subconjunto y no copia propiedades como `descripcion`, `placeholder` ni `textoAyuda`. `serializarBuilderModelAJson()` tampoco las emite. Más grave aún, las propiedades ricas del contrato v3 (`rutaDatos`, `activo`, `visible`, restricciones, reglas condicionales, referencia de cálculo, etc.) no tienen un mecanismo general de preservación.

### Decisión F6.0-DEC-03

F6.1 deberá introducir preservación lossless de metadatos no editables. El modelo de UI no será autorizado a destruir propiedades desconocidas/reconocidas-no-editables al reserializar.

## 8. Catálogos

### 8.1 Contrato canónico

Para F6, un catálogo embebido editable deberá tener como mínimo:

```json
{
  "codigo": "ESCALA_1_5",
  "nombre": "Escala 1 a 5",
  "elementos": [
    {
      "codigo": "1",
      "valor": "Muy bajo",
      "orden": 1
    }
  ]
}
```

Y un campo asociado deberá almacenar el **código**:

```json
{
  "clave": "impacto",
  "tipo": "selector-catalogo",
  "codigoCatalogo": "ESCALA_1_5"
}
```

La respuesta de evaluación debe persistir:

```json
{
  "impacto": "1"
}
```

No la etiqueta visible.

### 8.2 Reglas de integridad aprobadas para F6.1

- código de catálogo obligatorio;
- código único case-insensitive;
- nombre obligatorio;
- elementos como arreglo;
- código de elemento obligatorio;
- código de elemento único dentro del catálogo, case-insensitive;
- etiqueta/valor visible obligatorio;
- orden entero y determinista;
- un campo `selector-catalogo` o `catalogo-multiple` debe referenciar un catálogo existente;
- eliminar un catálogo referenciado debe bloquearse o exigir primero resolver referencias;
- cambiar la etiqueta de un elemento no cambia su identidad almacenada;
- códigos alfanuméricos son válidos;
- una respuesta histórica con código ya retirado no puede degradarse a `null` ni desaparecer.

### Decisión F6.0-DEC-05

**`codigo` es identidad persistida; `valor`/`etiqueta` es presentación.**

## 9. Respuestas de evaluación

El frontend vigente define:

`ValorRespuestaFormulario = string | number | boolean | string[] | null`.

Esto es compatible con:

- selector simple -> `string`
- selección múltiple -> `string[]`
- número -> `number`
- checkbox -> `boolean`
- ausencia -> `null`

### Decisión F6.0-DEC-06

F6.1/F6.4 no podrán convertir selección múltiple a índices/enteros de forma implícita. Los códigos de catálogo son cadenas y pueden ser alfanuméricos.

## 10. Round-trip canónico de F6

### 10.1 Definición

El gate final de F6 deberá demostrar:

1. cargar JSON;
2. normalizar para UI;
3. editar únicamente una propiedad autorizada;
4. serializar;
5. guardar por API;
6. recuperar el mismo `VER_JSON` semántico;
7. reabrir Builder;
8. comprobar que propiedades editadas cambiaron;
9. comprobar que propiedades no editadas permanecen semánticamente iguales;
10. comprobar que propiedades no soportadas por UI siguen presentes.

### 10.2 Evaluación

1. seleccionar códigos de catálogo;
2. guardar `EVA_DATOS_JSON`;
3. cerrar;
4. recuperar evaluación;
5. cargar la versión exacta `evaVersionId`;
6. resolver códigos contra el catálogo de esa versión;
7. mostrar las etiquetas correspondientes;
8. editar un valor;
9. volver a guardar/reabrir;
10. conservar todos los demás valores sin pérdida.
