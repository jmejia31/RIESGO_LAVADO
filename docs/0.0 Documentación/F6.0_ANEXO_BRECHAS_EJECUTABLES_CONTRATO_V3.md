# F6.0 — Anexo vinculante de brechas ejecutables contra contrato v3

**Proyecto:** RIESGO_LAVADO / SGRLA-IHSS  
**Módulo:** Matrices de Riesgos  
**Fase:** F6 — Catálogos y guardado bidireccional  
**Subfase:** F6.0 — Auditoría del contrato  
**Fecha:** 2026-08-19  
**Baseline de auditoría:** `7692c5fd14c3058b17b6245ca596b931ac844009`  
**Documento principal F6.0:** `F6.0_AUDITORIA_CONTRATO_JSON_CATALOGOS.md`  
**Naturaleza:** anexo de causalidad ejecutable; no sustituye ni reescribe el documento principal.

## 1. Propósito

El documento principal F6.0 fija la política de **cero pérdida silenciosa** y la diferencia entre el contrato funcional v3 y el Builder reducido. Este anexo agrega evidencia directa de código para convertir esa auditoría en gates reproducibles de F6.1.

El contrato v3 establece que `valorCatalogoAlmacenado = codigo`, `valorCatalogoPresentado = etiqueta`, la ausencia es `null`, la definición está versionada, la respuesta queda asociada a versión, las versiones publicadas son inmutables, los cálculos autoritativos pertenecen al servidor y los catálogos pueden provenir de servicio/base de datos con respaldo embebido.

## 2. Brechas ejecutables confirmadas

### F6-X01 — CRÍTICA — Builder `clave` vs validador backend `id`

El serializador `serializarBuilderModelAJson()` emite identidad de sección/campo con `clave`. `FormularioValidador.ExtraerCampos()` obtiene exclusivamente `campo["id"]` y omite el campo cuando no existe.

**Impacto:** una plantilla legacy con `id` puede abrir, normalizarse y volver a guardarse con `clave`; después el backend puede ignorar esos campos durante la validación.

**Gate F6.1:** `clave` será identidad canónica y `id` alias legacy de lectura. Debe existir prueba `legacy id -> Builder -> clave -> backend valida el mismo campo`.

### F6-X02 — CRÍTICA — `catalogo-multiple` frontend `string[]` vs backend `Int32[]`

Frontend admite `string[]` y el contrato v3 contiene códigos alfanuméricos. `FormularioValidador.ValidarTipo()` exige actualmente que cada elemento del array convierta a `Int32`.

**Impacto:** valores válidos como `["PEP","GEO-HN-01","PROD_001"]` pueden ser rechazados.

**Gate F6.1:** catálogo múltiple debe conservar códigos string sin coerción numérica.

### F6-X03 — CRÍTICA — `/metodologia/version/{id}` pierde metadata del renderer

`VER_JSON` se conserva completo en CLOB, pero los DTO actuales de metodología no exponen `columnasPorFila`, `opciones`, `formula`, `anchoColumnas` ni `tipoOriginal`.

**Impacto:** el CLOB puede estar íntegro mientras captura/reapertura pierde semántica porque el frontend consume la proyección de metodología.

**Gate:** `VER_JSON -> metodologia/version -> frontend` debe preservar toda metadata requerida por renderer.

### F6-X04 — CRÍTICA — Forma de catálogos v3 incompatible con `CatalogoMatrices[]`

El contrato v3 usa un objeto indexado por identificador, con `tipoOrigen`, `version`, `activo`, `origenPrincipal`, `origenAlternativoExcel`, `elementos`/`elementosRespaldo`. El runtime reducido espera `CatalogoMatrices[]` y el normalizador solo conserva `catalogos` cuando `Array.isArray(...)`.

**Impacto:** los catálogos v3 pueden desaparecer por completo al pasar por el normalizador reducido.

**Gate F6.1:** adaptador contractual explícito v3 ↔ modelo editable; preservar opacamente metadatos no editados.

### F6-X05 — CRÍTICA — Catálogos hardcodeados en Form Builder

`FormBuilderComponent.catalogosDisponibles` contiene una lista fija y el alta de `selector-catalogo` usa esa colección, no los catálogos reales de la versión.

**Gate F6.2:** después del cierre de F6.1, el selector debe derivarse del modelo/versión actual.

### F6-X06 — ALTA — Integridad referencial insuficiente

El validador frontend exige `codigoCatalogo` no vacío, pero no confirma existencia, duplicados case-insensitive, códigos vacíos, elementos duplicados ni referencias antes de eliminar catálogo.

### F6-X07 — ALTA — `catalogos`/`reglas` con normalización superficial

El normalizador reducido hace pass-through/cast de arrays sin normalización interna de identidad, orden, duplicados o metadata.

### F6-X08 — ALTA — Metadata Builder editable no serializada

`descripcion`, `placeholder` y `textoAyuda` existen en memoria del Builder, pero el serializador reducido no los devuelve al JSON.

### F6-X09 — ALTA — Vocabulario de tipos frontend/backend divergente

Frontend usa `selector-catalogo`, `checkbox`, `catalogo-multiple`; backend maneja `catalogo`, `booleano`, `catalogo-multiple` y deja tipos desconocidos por `default => true`.

### F6-X10 — ALTA — Respuesta v3 estructurada vs mapa reducido

El JSON Schema v1 define envelope con `identificadorFormulario`, `versionFormulario`, `identificadorRegistro`, `estado`, `flujoTrabajo` y `datos`, con objetos/repetidores/listas anidadas. El mapa reducido F5 representa escalares simples o `string[]` por clave.

**Gate:** F6 debe preservar documento/envelope y fijar el límite del renderer reducido; estructuras no editables no pueden destruirse.

## 3. Causalidad de persistencia

Puntos que hoy preservan contenido:

- versión crea/actualiza `VER_JSON` como CLOB completo;
- clonación conserva `VerJson` fuente;
- evaluación almacena `EVA_DATOS_JSON` y `EVA_DATOS_CALC_JSON` como CLOB.

Por ello, el repositorio CLOB no es el principal punto de pérdida detectado. Los puntos críticos son adaptación/normalización, serialización Builder, validación backend, proyección de metodología y catálogo hardcodeado de UI.

## 4. Gates obligatorios para F6.1

1. cargar contrato v3 sin perder envelope;
2. preservar `catalogos` objeto v3 con origen/version/respaldo;
3. preservar identidad estable `identificador` al proyectar a `clave`;
4. conservar metadata no editable de campos/secciones;
5. backend reconoce `clave` canónica e `id` legacy;
6. `string[]` alfanumérico es válido en multiselección;
7. metadata del renderer sobrevive `/metodologia/version/{id}`;
8. `0`, `false` y `null` permanecen diferentes;
9. catálogo inexistente/duplicado genera diagnóstico explícito;
10. tipo v3 aún no editable se preserva, no se degrada silenciosamente;
11. propiedad futura/desconocida se preserva o bloquea guardado con diagnóstico;
12. envelope de respuesta no se aplana destructivamente.

## 5. Precedencia

1. **Contrato funcional v3 validado del usuario:** semántica objetivo.
2. **Código ejecutable vigente:** compatibilidad que debe preservarse/migrarse.
3. **SQL legacy/documentación histórica:** entradas/antecedentes, no autoridad para degradar v3.

La migración será compatible hacia atrás en lectura y canónica hacia adelante en escritura, sin pérdida.

## 6. Cierre

Este anexo no modifica código productivo, Oracle ni contratos API. **F6.1 es la única siguiente subfase habilitada; F6.2 permanece bloqueada hasta que estos gates estén automatizados y verdes.**
