F5.1 consolida el núcleo técnico del renderer dinámico del módulo Matrices de Riesgos. Su alcance es exclusivamente contrato, arquitectura, normalización, renderizado, validación estructural y cobertura automatizada. ## 3. Arquitectura resultante

El renderer se divide en responsabilidades explícitas:

1. **Contrato/modelos**: modelos del módulo describen metodología, definición editable, secciones, campos, catálogos, reglas y respuestas.
2. **Normalización defensiva**: `utils/dynamic-form-renderer.util.ts` traduce aliases de contrato a una representación canónica segura.
3. **Renderer reutilizable**: `components/dynamic-field-renderer/dynamic-field-renderer.component.ts` representa cada campo con identidad estable, etiqueta, valor y estado de edición.
4. **Integración de página**: `matrices-riesgos.component.ts/.html` consume la definición normalizada y respuestas sin reconstruir manualmente cada tipo en el template principal.
5. **Pruebas por responsabilidad funcional**: utilidades, renderer aislado e integración del componente cuentan con suites semánticamente nombradas; no se utilizan nombres `*.f5.spec.ts`.

## 4. Tipos canónicos soportados

La normalización reconoce los siguientes tipos canónicos:

- `texto`
- `numero`
- `fecha`
- `texto-largo`
- `selector-catalogo`
- `radio`
- `catalogo-multiple`
- `checkbox`
- `formula`
- `desconocido` como fallback defensivo

El contrato admite aliases operativos en español e inglés. Los aliases se normalizan antes de renderizar y el tipo original se conserva cuando el tipo es desconocido.

## 5. Reglas defensivas implementadas

### 5.1 Definición

- JSON vacío o inválido no lanza excepciones: produce una definición estable sin secciones.
- Se aceptan nombres de propiedades de contrato equivalentes (`secciones/sections`, `campos/fields`, etc.).
- Secciones inválidas son descartadas.
- Campos inválidos o sin clave son descartados.
- Las claves de campo son únicas globalmente de forma case-insensitive; ante duplicados se conserva la primera definición.
- Orden, columnas y ancho de campo se normalizan a rangos seguros.
- Etiquetas ausentes utilizan la clave como fallback.
- IDs canónicos inválidos se normalizan a `null`.
- Opciones inline eliminan blancos y duplicados.

### 5.2 Tipos y edición

- Tipos desconocidos no se convierten silenciosamente en texto editable.
- Campos `formula` son forzados a solo lectura.
- Tipos desconocidos son forzados a solo lectura.
- `soloLectura/readOnly` y `obligatorio/required` aceptan formas de contrato compatibles y se normalizan a booleanos.

### 5.3 Respuestas

- Se preservan explícitamente `0` y `false` como valores válidos.
- `null` se conserva como ausencia explícita.
- Números no finitos se normalizan a `null`.
- Objetos arbitrarios no se aceptan como valores escalares y se normalizan a `null`.
- Selecciones múltiples eliminan blancos y duplicados y se normalizan a valores de texto seguros.
- JSON de respuestas inválido produce un objeto vacío estable.

### 5.4 Presentación segura

- La ausencia de valor se distingue de valores falsy válidos.
- La representación de solo lectura mantiene `0`, `Sí/No`, listas y ausencia `-` correctamente.
- La arquitectura no requiere insertar metadata dinámica mediante HTML arbitrario inseguro.

## 6. Contrato de identidad y estructura

Cada campo normalizado conserva una clave estable. El renderer recibe la definición ya normalizada y evita que el componente de página replique decisiones de tipo. Secciones se ordenan por metadata y cada campo mantiene ancho, etiqueta, código de catálogo, opciones, fórmula, obligatoriedad y estado de solo lectura cuando corresponde.

## 7. Cobertura automatizada

Las pruebas de F5.1 cubren, entre otros:

- nueve tipos canónicos y aliases operativos;
- tipos desconocidos;
- JSON vacío, válido e inválido;
- aliases bilingües del contrato;
- secciones incompletas o inválidas;
- orden y columnas fuera de rango;
- campos sin clave y claves duplicadas;
- fórmula y desconocido en solo lectura;
- catálogos, reglas y metadata opcional;
- IDs canónicos;
- opciones inline;
- metodología ausente;
- respuestas escalares, múltiples y serializadas;
- `0`, `false`, `null`, `NaN` e infinitos;
- evaluación de presencia de valor;
- formateo seguro de solo lectura;
- renderer reutilizable aislado;
- integración del renderer en la página Matrices de Riesgos.

El refuerzo final de cobertura se concentra en comportamiento real y ramas defensivas del contrato. No se reducen thresholds, no se agregan exclusiones y no se introducen no-ops productivos para alterar métricas.
