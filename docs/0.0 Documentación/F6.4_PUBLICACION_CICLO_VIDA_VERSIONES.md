# F6.4 — Publicación y Ciclo de Vida de Versiones

## 1. Resumen de Ejecución y Objetivos F6.4

La fase **F6.4 — Publicación y Ciclo de Vida de Versiones** consolida las reglas de negocio e invariantes críticas asociadas al ciclo de vida de los formularios de Matrices de Riesgo LAFT.

### Invariantes Certificados:
1. **C01 (Crítica - Inmutabilidad de Versiones Publicadas):**
   - Se prohíbe la eliminación de cualquier versión con estado `PUBLISHED` (sea actualmente vigente o histórica).
   - Solamente se permite la eliminación de versiones con estado `DRAFT` que **no** sean vigentes.
   - Implementado con triple capa defensiva:
     - **Frontend Template (`matrices-riesgos.component.html`):** El botón "Eliminar" se renderiza únicamente cuando `version.verEstado === 'DRAFT' && !version.verVigente`.
     - **Frontend TS (`matrices-riesgos.component.ts`):** Guard defensivo en `eliminarVersionFormulario` que valida `verEstado === 'DRAFT' && !verVigente` antes de invocar la API.
     - **Backend AppService (`MatricesRiesgosAppService.cs`):** Validador explícito que retorna HTTP 400 (`ServiceResult.BadRequest`) si la versión no es `DRAFT` o si es vigente.
     - **Backend Repository (`MatricesRiesgosRepository.cs`):** Sentencia SQL parametrizada con filtro defensivo estricto: `DELETE FROM RL_MR_VERSIONES_FORMULARIO WHERE VER_ID = :versionId AND VER_VIGENTE = 0 AND VER_ESTADO = 'DRAFT'`.

2. **C02 (Crítica - Unicidad de Versión Vigente por Concurrencia):**
   - Garantiza que **nunca** exista más de una versión vigente simultánea por familia de formulario.
   - En las operaciones de publicación (`PublicarVersionFormularioAsync`) y cambio de vigencia (`CambiarEstadoVigenciaFormularioAsync`), se ejecuta un bloqueo pesimista en la base de datos dentro de la transacción Oracle:
     ```sql
     SELECT FAM_ID FROM RL_MR_FAMILIAS_FORMULARIO WHERE FAM_ID = :familiaId FOR UPDATE
     ```
   - Previene carreras de condición serializando peticiones simultáneas de activación/publicación sobre la misma familia.

3. **C03 (Alta - Estado de Familia Activa):**
   - Se rechaza con HTTP 400 cualquier intento de publicar una versión perteneciente a una familia inactiva (`FamActivo == false`).

4. **C04 (Alta - Estado Previo a Activación):**
   - El método `CambiarEstadoVigenciaFormularioAsync` en AppService valida explícitamente que la versión tenga estado `PUBLISHED` antes de permitir la alternancia de vigencia.

5. **C05 (Alta UX - Modal Informativo SweetAlert2):**
   - El diálogo de confirmación de publicación SweetAlert2 detalla explícitamente en viñetas HTML que la versión actual vigente pasará a ser histórica y que la nueva versión quedará en modo de solo lectura.
