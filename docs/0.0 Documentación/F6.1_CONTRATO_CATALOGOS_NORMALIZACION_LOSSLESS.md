## Alcance

F6.1 convierte la auditoría F6.0 en un contrato ejecutable para el Form Builder y los catálogos dinámicos. La regla rectora es **cero pérdida silenciosa**: cualquier propiedad válida de una definición que el Builder todavía no edite debe preservarse opacamente durante el ciclo JSON → Builder → JSON.

## Fuente contractual

La implementación se fundamenta en la auditoría F6.0 y en el contrato funcional v3 suministrado para formularios dinámicos. Se preservan las decisiones rectoras: definición versionada, versiones publicadas inmutables, respuestas ligadas a versión, catálogos autoritativos, valores persistidos por código y separación entre código almacenado y etiqueta presentada.

## Cambios técnicos

### 1. `form-builder.models.ts`

Se incorporó una representación lossless del contrato:

- snapshot JSON opaco de raíz, sección, campo, catálogo y elemento;
- soporte de definición compacta y envelope con `definicionFormulario`;
- preservación de la forma original de catálogos (`array` o `map`);
- preservación de dialectos de identidad (`clave`, `rutaDatos`, `identificador`);
- preservación de dialectos de referencia de catálogo (`codigoCatalogo`, `catalogoCodigo`, `catalogo`);
- preservación de propiedades conocidas como `descripcion`, `placeholder` y `textoAyuda`;
- preservación de propiedades futuras/no soportadas mediante merge sobre el snapshot original;
- soporte de aliases de tipos actuales y del contrato rico;
- tipos todavía no editables se degradan únicamente para visualización del Builder, conservando `tipoOriginal` para reserializarlos sin pérdida si no se modifica el tipo;
- normalización de catálogos en forma array/map y compatibilidad con `elementos` / `elementosRespaldo`;
- códigos de catálogo y elemento se mantienen como `string`, incluyendo códigos alfanuméricos.

### 2. `form-builder-validator.util.ts`

Se endureció la validación contractual:

- código de catálogo obligatorio;
- unicidad de código de catálogo case-insensitive;
- nombre visible obligatorio;
- código y valor de elemento obligatorios;
- unicidad de código de elemento dentro del catálogo, case-insensitive;
- `orden` de elemento entero y >= 1;
- `selector-catalogo` y `catalogo-multiple` deben referenciar un catálogo existente;
- se preservan las reglas existentes de claves de campo y etiquetas;
- se evita exigir una fórmula artificial a tipos ricos preservados mediante `tipoOriginal`.

### 3. `form-builder.roundtrip.spec.ts`

Nueva suite semántica, nombrada por responsabilidad y no por número de fase. Contiene 5 pruebas dedicadas:

1. preservación de metadatos conocidos y futuros al editar una propiedad soportada;
2. preservación de envelope/dialecto v3 y catálogos en forma de mapa;
3. preservación de tipos aún no editables, por ejemplo `REPETIDOR`;
4. detección de duplicados, orden inválido y referencias de catálogo inexistentes;
5. aceptación de códigos alfanuméricos sin coerción numérica.
